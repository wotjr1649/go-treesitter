# ADR-0027 — One pinned generator CLI for every grammar

**Status:** Accepted by the owner · 2026-11-16 · implemented in `tools/gen` · amends ADR-0020 decision 1
(grammar `parser.c` is generated by us from unmodified upstream grammar inputs instead of taken as committed).

## Context

Each upstream grammar repository commits a `src/parser.c` generated by whatever tree-sitter CLI its contributors
used. The 23 repositories we pin declare CLI ranges across five minor versions (`^0.24` to `^0.27`); the CLI writes
no version into `parser.c` since 0.26.1, so the producer of most committed parsers cannot be read from the file.
Upstream CI verifies `tree-sitter generate` with the latest CLI release, while contributors regenerate with the
repository's own CLI, so committed parsers drift from what CI checks. Before this decision, we compiled the
committed `parser.c` except where a patch or an LFS-only parser forced regeneration with our pinned CLI (bash, python, ruby, yaml,
postgres).

The owner wants every module produced by one generator. A local measurement on 2026-11-16 (Windows amd64, CLI
0.27.2, then-current pins; maintainer-local evidence archive `2026-11-16-s17-cli-uniformity`, not in this repository) regenerated all 24
grammars and compared them with the C we use:

- `parser.c` changed for 20 grammars; `node-types.json` static changes for 12; nine grammars move from parser
  ABI 14 to 15.
- Native trees on our pinned corpora (4,616 inputs, 13,188 seeded edits) were identical for 23 grammars. C# changed
  one corpus tree and two edits, one of each from clean to error (`case int when …`); its own upstream test
  "Switch statements" fails. The change starts with the CLI 0.26.12 generator.
- Engine parse time on four grammars changed by −4 % to +10 % (no consistent gain); ADR-0022 memory was unchanged.
- Generation took about 9 minutes per full set on one runner (PostgreSQL 7 minutes, 4.5 GiB peak).
- cpp, typescript and tsx need other grammars from npm to evaluate `grammar.js`; YAML's C patch must be applied
  after generation.

Large consumers (nvim-treesitter, Helix, Zed) compile the committed `parser.c` and regenerate only parsers that
have none.

## Decision

1. **One pinned CLI.** Every grammar module's C is generated from its pinned, unmodified grammar inputs with the
   single tree-sitter CLI pinned in `tools/gen/pins.json`. The committed upstream `parser.c` becomes the comparison
   reference, not the build input.
2. **Deliberate moves.** The CLI pin moves only in a pin-move pull request, never automatically on a CLI release.
   The upstream watch reports new CLI releases.
3. **Behaviour gate per grammar.** When the CLI or a grammar pin moves, a grammar uses the regenerated C only if, on
   its pinned corpus, seeded edits and large inputs, native trees from the regenerated C equal those from the
   reference C, and the upstream repository's own tests do not newly fail. A grammar that fails keeps the reference C
   and is listed as an exception in `pins.json` with the failing inputs, until the owner accepts the difference in the
   pull request or upstream changes. `node-types.json` changes are reviewed and recorded in the schema register.
4. **Order and inputs.** `grammar.js` patches apply before generation and C patches (ADR-0023) after it. npm
   dependencies of `grammar.js` come from the upstream lockfile, verified by integrity hash, without install
   scripts, and are recorded in provenance.
5. **Retired initial exception.** The previous C# pin retained committed C under decision 3 because CLI 0.27.2
   changed switch type-pattern parsing. With the [upstream v0.24.0 pin](https://github.com/tree-sitter/tree-sitter-c-sharp/releases/tag/v0.24.0),
   the pinned CLI's output equals the committed C and the exception is removed. The `regen.yml`
   C# shard runs the full generator behaviour gate, including the upstream tests.

## Consequences

- `tools/gen` regenerates non-exception grammars with the pinned native QuickJS runtime. npm grammar inputs from
  upstream lockfiles are supplied in each grammar's working-directory `node_modules`. From the first owner-source
  move, TypeScript and TSX read their JavaScript grammar from the shared archive under
  [ADR-0024 rule 7.7](ADR-0024-grammar-source-tiers.md#amendment-2026-11-18-rule-7-owner-maintained-repositories).
  Input patches precede generation, and C patches follow it. The native behaviour gate is
  `tools/native-ref/generatorgate.py`; regeneration CI runs it and retains its reports and timing/RSS receipts.
  Adoption remains subject to the recorded validation gates, including hosted drift and resource measurements.
- Moving the CLI becomes a reviewed event with a gate, comparable to a grammar pin move; regeneration CI includes
  deterministic generation and native behaviour checks.
- Upstream contributions still use each repository's own CLI for regenerated files (ADR-0025 amendment of
  2026-11-16); this ADR concerns only the C we build.

## Swift amendment (owner, 2026-11-17)

Swift has no committed parser C and pins `reference: "none"`; the gate records
`NOT_APPLICABLE_NO_COMMITTED_PARSER` for that comparison. It still requires two independent generations,
strict schema validation, product/fresh-native corpus, seeded edits, field lookups and pinned large-input checks.

Swift alone selects `generateFrom: "grammar.json"`: the pinned CLI reads the unmodified upstream-committed
`src/grammar.json`, including emoji patterns, without evaluating `grammar.js`. The native runtime selection,
archive identity and all tool/source revisions stay pinned. Generation provenance records the input choice and
its original SHA-256, and native-ref uses the same common preparation path. This avoids Swift's version-detection
fallback under native QuickJS, which omits the emoji patterns when evaluating this revision's `grammar.js`.

The owner accepts one upstream-test exception: CLI 0.27.2's
`tree-sitter test` query runner uses `test/outline/outline.swift` as the query path instead of `queries/outline.scm`.
The gate retains full-suite exit 1 and `Query compilation failed` / `Invalid syntax: import Foundation`, requires
312/312 corpus cases and all eight highlight cases to pass, and additionally runs the correct command:
`tree-sitter query queries/outline.scm test/outline/outline.swift`. That command must succeed. No corpus exclusion,
expected-tree change or grammar patch is accepted. A new failure, stale signature or CLI pin change fails the
exception check. When the CLI pin moves to a fixed version, rerun the full suite and remove this exception after
it succeeds. This development exception does not approve a release.

## Grammar-input patch comparisons (ADR-0023)

The generator gate's reference omits grammar-input patches and retains the same recorded C/header fixes as
its candidate. A committed parser remains the reference; an LFS parser is regenerated from unpatched grammar
inputs, must match the committed SHA-256 OID **before** C/header patches apply, and is then built independently.
Candidate sharing still requires no patches and identical C/header inputs.

Deliberate grammar-input fixes record their reviewed behaviour differences beside the patch in
`tools/gen/patches/<grammar>/generator-expectations.json`, rather than in `pins.json`: pins identify build inputs;
this sidecar identifies the exact permitted comparison results. It binds the grammar archive/commit, runtime
commit, CLI, complete patch records, seed, corpus/edit manifests, patch-corpus files and that grammar's own entries in the pinned large-input manifest. Each difference
records its input ID/identity and both result SHA-256 signatures. Corpus/large signatures hash the dump bytes;
edit signatures hash canonical JSON of the result row (excluding `edit_ms`) plus ranges/fields hashes, including
the incremental/fresh dump hashes. Upstream signatures hash canonical JSON of each changed outcome or complete
same-name failure list, including improvements. Canonical JSON uses sorted keys, compact separators, UTF-8 and
unescaped Unicode. Duplicate upstream outcome identities fail.

The actual and recorded difference lists must match exactly, including all fields: new, changed or disappeared
differences, stale identities and malformed records fail. Without an expectation file, the zero-difference rule remains.
The gate never writes or refreshes expectations automatically. A sidecar requires a reason and retirement condition,
is reviewed with the patch, and is retired or reviewed anew when upstream inputs, CLI or patches change.

A patch can retain regression inputs in `tools/gen/patches/<grammar>/corpus/*.txt` (tree-sitter corpus format).
The gate adds them to a private copy of each native corpus under a `grammar-patch-` filename prefix without
replacing upstream files, then ciconf generates the same three seeded edits per input. The original upstream-only
corpus remains the source for pinned concat large inputs. These original repository fixtures are separate
from upstream test expectations and the pinned grammar-kit projection; their hashes are recorded in the sidecar
identity and execution report. They ensure behaviour-changing fixes are exercised even when upstream seeds are ASCII.

## Nightly rehearsal (2026-11-20, report only)

The owner wants every grammar to be served with the latest tree-sitter CLI. Decision 1 and 2 stay: the CLI that builds
the product is the pinned one and moves only in a pin-move pull request. To see early what a move would change,
`.github/workflows/nightly-cli-rehearsal.yml` runs weekly (and on dispatch) on hosted Linux amd64 and regenerates every grammar
a second time with the CLI of the `nightly` release of `tree-sitter/tree-sitter`, through the same preparation path as the
pinned run (verified archive, grammar-input patches, double generation, C patches).

- **Report only.** It reports, per grammar, whether generation succeeded and was deterministic, which of `parser.c`,
  `grammar.json`, `node-types.json` and other generated files (the `tree_sitter/*.h` headers come from the CLI, so they
  carry the nightly runtime's changes) differ from the pinned-CLI output, and the `node-types.json` schema diff summary
  (codes and risks of `gen schema diff`). It never edits the repository, opens a PR, moves a pin or fails a PR. It is not
  a gate and not parity evidence (`validation.md`, E2); it does not run the conformance corpus, which needs the native
  build lane and belongs to the pin-move pull request. The rehearsal regenerates every grammar and leaves
  the committed reference C untouched.
- **Identity instead of a pin.** The nightly assets have no fixed bytes. The run records the asset URL, the API size and
  GitHub's own `digest` of the asset, the commit of the `nightly` tag read before and after the download, the SHA-256 of
  the downloaded `.gz` and of the binary that ran, and its `--version` line. These are cross-checked, not pinned: the API
  size and digest must match the downloaded file (checked before it is decompressed or run), the tag must not move
  between the two lookups, and the build commit named by `--version` must be that tag commit. Missing or mismatched
  identity, including an unreadable asset or metadata file, unparsable metadata or an asset that does not decompress, is
  recorded and **holds** the comparison: no grammar is compared, the run is red and the tracking issue is not updated.
  That identity is the only thing a result is bound to.
- **Isolation.** The token only reads the release metadata, in its own step, before anything downloaded runs; the step
  that runs `gen` has no token, also in the local `all` path. The pinned archives and npm inputs are fetched and verified
  first by trusted code. Every nightly execution (`--version`, `generate`) runs through `tools/gen/nightly-sandbox.sh`
  in bubblewrap: no network, an empty environment, no new privileges, its own PID namespace, and a filesystem of
  read-only `/usr`, that call's prepared tree (grammar, patched inputs, npm inputs, Swift's `grammar.json`) read-only, and
  a fresh `generate --output` directory as the one writable path; the other tree, the checkout, pins, patches, archives,
  Go cache and runner files are not mounted. Trusted code imports only the files that generation mode writes (regular
  files with the names `tree-sitter generate` writes; never `grammar.json` when it is the input) into the tree, removes
  an expected file the CLI did not write instead of keeping the archive's copy, then applies C patches, hashes and
  assembles the report. Independently of the sandbox, `gen` gives the nightly `--version` and `generate` processes no
  GitHub token variables and no stale mount variables; only `generate` gets the two trusted mount paths. A workflow
  self-check with the same mount layout proves the inputs are read-only, the other tree and runner files are absent, the
  token and network are absent and the output is writable; each of its checks fails the step on its own. Without the
  wrapper nothing downloaded runs, except with an explicit local opt-in (`-nightly-unsandboxed`, recorded as
  `"sandbox": "none"`).
- **Comparison.** The common input check is Prepare's own pre-generation part (archive, input patches, npm inputs,
  generation input), plus `grammar.js` in the generate directory when no `generateFrom` is set; its failure is
  `input-failed` and neither CLI runs. Then the pinned and the nightly preparation run
  independently and each outcome is reported (`pinned-failed`, `nightly-failed`, `both-failed`); files are compared only
  when both succeed. Copies of the differing main files are kept for the sides that have them; whenever both succeed the
  schema verdict is given, `identical` only for equal hashes and `BLOCKED`, with its reason, when one or both sides lack
  the file or it is unreadable.
- **Separate code path.** The pinned path is unchanged: `grammarpatch.Config` verifies the pinned archive and binary
  hash and the version unless `Config.Unpinned` is set, which only `gen nightly-rehearsal` does, and which refuses a
  Config that also carries pin fields. `gen -lang`, `regen.sh` and `regen.yml` cannot reach it.
- **Tracking issue.** One comment on #67 (the CLI/runtime move to 0.28.0) when the per-grammar results changed
  since the last comment; the digest is kept in a hidden marker at the end of that comment and covers the results
  (status, each differing file with its change kind and both SHA-256s, the schema verdict with its per-code and per-risk
  counts), not the nightly identity, error text or timings. Only a successful rehearsal with a verified identity can
  comment; only the workflow bot's own marked comments are read, and a failed lookup fails the issue job without
  commenting. Nothing is posted once #67 is closed. A broken harness (for example an unreachable download) fails that
  scheduled run only.
