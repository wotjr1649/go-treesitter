### PostgreSQL Korean support (v0.6.0)

v0.6.0 uses [upstream v19.0.0](https://github.com/gmr/tree-sitter-postgres/releases/tag/v19.0.0) of
`gmr/tree-sitter-postgres` under ADR-0024 rule 4. [Upstream PR #102](https://github.com/gmr/tree-sitter-postgres/pull/102)
fixed both defects from [upstream issue #101](https://github.com/gmr/tree-sitter-postgres/issues/101).
The [retirement record](../../tools/gen/patches/postgres/README.md) identifies the two temporary patches
that provided the same fixes at the previous development pin. [Upstream PR #103](https://github.com/gmr/tree-sitter-postgres/pull/103)
refreshes the documentation SQL corpus for PostgreSQL 19.0.

Unquoted identifiers accept all non-ASCII code points, including NFD combining marks, supplementary
characters and U+3000, with the same ASCII start and continuation rules. `SELECT값` forms one identifier.
A standalone `SELECT값;` has a syntax error, while `SELECT SELECT값;` is clean. Dollar-quote tags compare
full code points. `$끝$…$끝$` closes and `$걁$…$A$` stays unmatched. The scanner caps tags at 63 code
points, while PostgreSQL accepts longer tags.

The grammar's `\s+` extras skip only ASCII whitespace. In `SELECT 　;` and `SELECT 　값;`, U+3000 belongs
to the identifier. `SELECT　값;` remains an invalid standalone name. `SELECT a　FROM t;` is clean and
treats `a　FROM` as one identifier with alias `t`, so a clean tree can conceal an unintended IME separator.

The grammar accepts adjacent numeric or parameter aliases such as `SELECT 9name;`, `SELECT 9값;`,
`SELECT $9END$body$9END$;` and `SELECT $9끝$body$9끝$;`. The last two examples parse as a parameter
plus alias. PostgreSQL rejects these inputs as trailing junk. Coverage is limited to PostgreSQL SQL and
the retained valid UTF-8 cases. The [fresh and incremental regression tests](../../tools/conformance/postgres_patches_test.go)
run under the `TestScannerPatches` CI filter.

## Swift (v0.6.0)

`grammars/swift` uses the tier-3 MIT `alex-pinkus/tree-sitter-swift` pin `a1d4a7b80260bf960f9e25198cddecbe5e6c46aa`
(the nvim-treesitter pin at adoption) for its first release. Upstream commits no
`parser.c`; `regenerate: true`, `generateFrom: "grammar.json"` produces C from the unmodified upstream-committed
`src/grammar.json` with pinned CLI 0.27.2, twice independently,
for both engine and native reference. The JSON includes emoji patterns; `grammar.js` is not evaluated.
There are zero upstream patches. No Swift language-version coverage is claimed.

The upstream scanner answers a failed state allocation with `fprintf(stderr, ...)` and `exit(1)`. In the engine this is the
WASI `proc_exit` import, which the host turns into a trap: the parse returns `EngineFault` (`ResourceLimit` after a refused
`memory.grow`), the instance is recreated, trees of the old instance are invalidated, and the next parse succeeds. The
stderr message is dropped. A historical local scratch build (before the JSON-input amendment) whose scanner returns NULL from `calloc` on each instance's second scanner
creation exercised that exact branch (Windows amd64, 40 MiB instance limit): each failing parse returned `EngineFault`
with `wasi proc_exit(1)`, the next parse and snapshot were clean, and no engine region remained after `Close`. Exhausting
a 32 MiB instance by input size did not reach the scanner branch: the first failure came from the runtime's own
allocator (`unreachable` trap, reported as `ResourceLimit`), and the next parse also succeeded. The scratch build is not
part of the repository.

The JSON-input candidate has local Windows amd64 E5 comparison against a fresh native C build: 312 corpus inputs,
936 seeded edits with changed ranges, 3,315 fresh and 8,715 edited-tree field result rows, and three pinned large
inputs (546,079 bytes), zero differences. Six edits differ between incremental and fresh in native C as well;
each product mode matches the same native mode. This does not claim incremental=fresh for every edit.
Local E4 on the three [workload-register](../validation/workloads.md#swift-candidate) files: large-input geomean
1.506x native across paired round/file measurements and 1.494x across per-file medians (criterion 2.5x), peaks
21.6–39.7 MiB against limits of 68.2–104.5 MiB, private growth at most 2.6 MiB, every engine region returned.
Five paired speed rounds with five timed reps each and three fresh processes per memory operation were used.
All 312 small-corpus files in that local run passed on the first pass. The [v0.6.0 gate board](release-critical-status.md#v060-preparation-gates)
records the hosted candidate runs, including Swift on Linux amd64/arm64 and macOS arm64.

Swift's upstream corpus passes 312/312, including emoji, and all eight highlight cases pass. The full CLI 0.27.2
suite still exits 1 at its outline query step: the CLI passes `test/outline/outline.swift` as the query path and
reports `Query compilation failed` / `Invalid syntax: import Foundation`. The owner approved only this exact
upstream-test exception on 2026-11-17. The gate retains the original failing log and exit, ratchets the signature,
and requires `tree-sitter query queries/outline.scm test/outline/outline.swift` to succeed. Any other failure or a
stale exception fails. Retire the exception after a CLI pin move fixes the full suite; it is not a parser-correctness
waiver or release approval. See [ADR-0027](../design/decisions/ADR-0027-one-pinned-generator-cli.md#swift-amendment-owner-2026-11-17).
