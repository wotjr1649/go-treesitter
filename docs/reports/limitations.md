# Preview limitations (v0.2.0)

What the preview does not do or has not shown. Gate results and their evidence levels are on the
[status board](release-critical-status.md); this page lists the edges of them. Nothing here is release-approved.

| # | Limitation | Evidence |
|---|---|---|
| 1 | **Released scope is wave 1:** C#, T-SQL, TypeScript, TSX, Python, Go, JSON. Wave-2 batch 1 adds development candidates JavaScript/JSX (one `javascript` module), HTML, CSS, Java, C, Rust, Bash and C++ (`cpp`). All eight passed the local Windows gates. Hosted gates for these candidates have not run. The remaining wave-2 grammars follow in later batches, one minor release each. | [status board scope](release-critical-status.md#scope), [`MIGRATING.md`](../../MIGRATING.md), [corpus/edit/query gates](../../tools/conformance) |
| 2 | **C agreement holds only on the listed inputs:** the session corpus (1,586 inputs), the grammars' own `test/corpus` (943 inputs, 2,829 seeded edits) and the seeded edit cases, compared with a native C build of the same pinned sources. It is not a guarantee for other inputs. | [status board gates](release-critical-status.md#wave-1-gates-session-15-windows-amd64-working-tree-grammar-modules-generated-by-toolsgen), [`oracle.md`](../specs/oracle.md), [`tools/conformance`](../../tools/conformance) |
| 3 | **Incremental may differ from fresh where native C does.** Five T-SQL edit cases differ in native C v0.27.2 and in the engine alike; they are ratcheted, not fixed. | [`known-regressions.md`](../validation/known-regressions.md#status-after-adr-0022), `knownIncrementalDiffs` in [`edits_test.go`](../../tools/conformance/edits_test.go) |
| 4 | **`Match` is experimental and lives outside the stable API** in the `experimental/match` package (`match.Match`, same module, no compatibility promise). Accuracy was measured as 100 % on large single-token edits and 77-97 % matched (0.1-0.3 % wrong) on small edits, and it is weak when the edit produces ERROR recovery. It may change or be removed. | [`api-v2.md` §7](../design/api-v2.md#7-primitives-that-set-this-library-apart-v001), doc comment in [`experimental/match`](../../experimental/match/match.go) |
| 5 | **Queries: RE2, not Rust regex; indexing cost; ABI 2 only.** `#match?` uses Go `regexp` (RE2); patterns whose meaning differs from the tree-sitter CLI's Rust regex (for example Unicode `\w`) can match differently. The first `Matches` call on a tree indexes the whole tree (O(nodes), whatever the byte range); the index of the last queried live tree stays allocated (< 32 B per node) and counts against `WithMaxMemoryBytes`. `#any-*` predicates are validated and exposed as properties but do not filter, as in CLI 0.27.2. Queries need grammar modules built for engine ABI 2 (v0.2.0 and later); v0.1.0 grammar modules still parse but `NewQuery` returns `ErrQueryUnsupported`. Live per-node navigation, included ranges and legacy encodings are not implemented. Raw query matches agree with native C on 22,047 query/input pairs (Windows) and 12,584 per platform in CI (Linux x64, arm64). | [`query-abi.md`](../design/query-abi.md), [`query_native_test.go`](../../tools/conformance/query_native_test.go), [`api-v2.md` §8-9](../design/api-v2.md#8-queries-v01-signatures-fixed-now) |
| 6 | **Hardware faults are not recoverable.** A generated-code trap becomes a `*ParseError` (`EngineFault` or `ResourceLimit`) and the instance is recreated; a hardware fault on unmapped memory is not a Go panic and cannot be captured. The memory provider keeps every reachable address committed or bounds-checked. | [`Call` in `internal/engine/memory.go`](../../internal/engine/memory.go), [`engine-abi.md`](../design/engine-abi.md) |
| 7 | **Speed and memory are measured on the CI hosts only:** Windows amd64 (local, large-input geomean 1.356x native), Linux x64/arm64 and macOS arm64 (bench lane, limit 2.5x, memory peak and release). On macOS the private-bytes gate subtracts heap pages the Go runtime has returned but the OS footprint still counts (ADR-0022 §3 macOS amendment; golang/go#47656). Windows arm64 is not benchmarked. C-reference conformance runs in CI on Linux x64/arm64 and Windows x64 for the corpus-derived inputs only. | [status board](release-critical-status.md), [ADR-0022](../design/decisions/ADR-0022-wave1-preview-versioning-and-release-memory-criterion.md), [`bench.yml`](../../.github/workflows/bench.yml) |
| 8 | **Balancing-cancel coverage uses test-only probe builds and sampled callbacks.** The retained generator and conformance lane cover all seven grammars, require a stop in balancing for each grammar, compare every next parse with native C, and require JSON's no-reset negative control to mismatch. The local Windows run passed for all seven; this observes instrumented builds and deterministic callback samples, not product module bytes or every callback. Hosted Linux (x64) run 43583147260 passed with the same callback counts and balancing boundaries as Windows. | [`TestBalancingCancel`](../../tools/conformance/balance_test.go), [probe harness](../../tools/conformance/balanceprobe/probe.go), [test-only ABI boundary](../design/engine-abi.md#test-only-balancing-cancel-lane), [nightly/manual Linux lane](../../.github/workflows/balancing-cancel.yml) |
| 9 | **`HasInvalidUTF8` is Go's `utf8.Valid`, not a tree-sitter notion.** It reports `!utf8.Valid(src)`. Invalid bytes are parsed like C (decode errors in the tree); `WithStrictUTF8` rejects them instead. 189 invalid-UTF-8 inputs agree with native C. | [`parser-result.md` § Input](../specs/parser-result.md#input), [`utf8_test.go`](../../tools/conformance/utf8_test.go) |
| 10 | **The zero `Node` is a null node, not an error.** `Node{}` is C's null node (for example from `DescendantForByteRange` when `start > end`). Every method on it returns its zero value (false, 0, `""`, the zero `Node`, an empty iterator, `(Node{}, false)`) and does not panic, so a null node can flow silently through code; check `IsZero` where a null node must be told from a real one. | doc comment in [`node.go`](../../node.go), [`parser-result.md`](../specs/parser-result.md#ownership-lifetime-concurrency) |
| 11 | **Scanner character functions follow wasi-libc semantics.** The native reference uses the same pinned wasi-libc character classification and case conversion as the engine. A native build using glibc or UCRT functions can differ for non-ASCII input. | [`oracle.md`](../specs/oracle.md), [`tools/native-ref`](../../tools/native-ref) |

Release authority, tags and publication are separate from this list: see
